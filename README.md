# SpoMon

SpoMon — внутренняя система банка для работы с сообщениями о подозрительных операциях
(СПО, финансовый мониторинг / AML). Заменяет ручной процесс: СПО в XML-файлах, разбросанные
по личным папкам сотрудников, без единой базы и без возможности быстро ответить на запрос
регулятора о конкретном клиенте.

Приложение разбирает XML-файлы СПО в единую БД, сопоставляет записи с уникальными клиентами
по документу/ИНН, вызывает Claude API для нормализации описаний, поиска паттернов и извлечения
контрагентов (NER), строит граф связей между клиентами через общих контрагентов и даёт
UI-реестр клиентов с карточкой и историей СПО. Подробности архитектуры и предметной области —
в [CLAUDE.md](CLAUDE.md).

## Требования

- PHP 8.1
- MySQL
- Composer

## Установка

```bash
composer install
cp .env.example .env
php artisan key:generate
```

Настройте подключение к БД в `.env` (`DB_DATABASE`, `DB_USERNAME`, `DB_PASSWORD`), затем
примените миграции:

```bash
php artisan migrate
```

## Обработка СПО

XML-файлы СПО (формат `form_101`) проходят через папку `storage/app/spo`:

- `storage/app/spo/incoming/` — сюда кладутся новые файлы на обработку;
- `storage/app/spo/processed/` — успешно обработанные файлы переносятся сюда;
- `storage/app/spo/failed/` — файлы, которые не удалось разобрать (неверный формат,
  повреждённый XML и т.п.), переносятся сюда; причина ошибки сохраняется в БД
  (таблица `spo_file_ingestions`, поле `error_message`).

Обработка запускается командой:

```bash
php artisan spo:ingest
```

Команда разбирает все `*.xml` файлы из `incoming/`, создаёт/находит клиентов по
документу/ИНН и сохраняет распарсенные записи СПО. Обработка идемпотентна: файл с уже
обработанным содержимым (по sha256-хешу) не парсится повторно. Команду можно запускать
многократно, в том числе по расписанию (по мере поступления новых файлов в `incoming/`).

## Матчинг клиентов

Матчинг реализован в `App\Repositories\ClientRepository` и делает следующее:

- **Юрлицо** — только точное совпадение по `tax_pay_number`. Fuzzy-логика для юрлиц не
  применяется вообще (в реальных данных встречаются "грязные" названия компаний,
  которые сравнивать по тексту бессмысленно — см. CLAUDE.md).
- **Физлицо**:
  1. Если у стороны есть `doc_number` — ищем точное совпадение по нему. Найдено —
     это тот же клиент, дальше не идём.
  2. Если точного совпадения нет (документа не было или он не найден в базе) и известна
     дата рождения (`dob`) — среди клиентов с той же датой рождения ищем максимально
     похожее ФИО (нормализованное через `App\Support\NameNormalizer` — регистр и
     пробелы, без транслитерации) с помощью `similar_text()`. Совпадение >= 85% —
     тот же клиент.
  3. Иначе — создаём нового клиента.

Без `dob` fuzzy-поиск не запускается: совпадение по одному лишь ФИО без даты рождения
даёт слишком много ложных срабатываний.

## Интеграция с Claude API

После каждой новой записи СПО (`SpoFileIngestionService`) в очередь ставится
`App\Jobs\ComputeClientCardJob` — он асинхронно пересчитывает карточку клиента
(`client_cards`), чтобы не блокировать обработку файла. Запускается воркер очереди:

```bash
php artisan queue:work
```

Что делает джоб:

- Загружает всю хронологическую историю СПО клиента (не только новую запись — единица
  вызова Claude API — это клиент целиком, см. CLAUDE.md).
- Считает `history_fingerprint` (sha256 от отсортированного списка id всех `spo_raw`
  клиента). Если у клиента уже есть карточка с таким же fingerprint — история не
  изменилась, и Claude API повторно не вызывается (идемпотентность).
- Иначе вызывает `App\Services\Llm\ClaudeApiClient::analyzeClient()` — HTTP-запрос к
  `https://api.anthropic.com/v1/messages` через `Http`-фасад (без стороннего SDK), модель
  принудительно вызывает инструмент `submit_client_analysis`, чтобы результат был
  structured JSON: переписанные в единый стиль описания, отметка о повторяющемся
  паттерне/нарастании частоты, извлечённые контрагенты (NER, пока только для аудита —
  раскладка в `entities`/`entity_mentions` появится на Этапе 5) и итоговая риск-метка
  (`App\Enums\RiskLabel`).
- Сохраняет результат в `client_cards` (`updateOrCreate` по `client_id`), включая полный
  сырой ответ API (`llm_raw_response`) для аудита.

Реестр уже известных сетевых сущностей (`known_network_entities`), который на этом этапе
всегда передаётся пустым, подключится на Этапе 5 (граф связей через `entity_mentions`).

Для работы нужно указать в `.env`:

```
ANTHROPIC_API_KEY=sk-ant-...
ANTHROPIC_MODEL=claude-sonnet-5
```

## Статус проекта

Реализовано:

- Этап 1: структура Laravel-проекта, enum'ы, миграции БД, модели.
- Этап 2: парсер XML `form_101`, идемпотентная загрузка файлов из `storage/app/spo`,
  команда `spo:ingest`.
- Этап 3: `ClientRepository`, fuzzy-матчинг клиентов по ФИО+ДОБ (см. "Матчинг клиентов" выше).
- Этап 4: интеграция с Claude API — `ClaudeApiClient`, `ComputeClientCardJob`, идемпотентный
  пересчёт карточки клиента (см. "Интеграция с Claude API" выше).

Впереди:

- Этап 5: карточка клиента, реестр сущностей и граф связей.
- Этап 6: API-эндпоинты и Livewire UI.
